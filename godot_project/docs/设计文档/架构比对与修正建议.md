## 2. 差异归类

### ✅ 一致且健康（保留）
单引擎、兼容性渲染、数据驱动 `.tres`、7 事件总线、Web 优先、本地优先存档理念——这些是 E-25 的「原则层」，实际代码守住了。

### 🟢 实际比文档更优（应正式化，不回退）
- **后端选自建 Express + SQLite**：对单人 / MVP 最务实——零外部账号、可离线开发、无厂商锁定、单文件数据库零运维、迭代最快。E-25 当年假设 Supabase「5 分钟启动最省事」，实际落地证明自建更贴合当前体量。
- **纯 GDScript**：当前 2D 体量无 C# 性能瓶颈，省去 .NET 运行时包体与编译链，正确。
- **系统有机膨胀（33 单例）**：勋章 / 结局 / 时间线 / 知识库 / 工具 / 背包等是真实演进出的功能，比文档拍的 24 子系统更贴需求。

### 🟡 文档漂移（目标态记本文，E-25 暂不修）
24 子系统映射、16 autoload 计数、7 模块目录结构全部过时；ADR-#5（Supabase）应被 Supersede；i18n / 广告 / 分析标「已接受」但代码未做，应改 Deferred。

### 🔴 真实风险（必须决策）
1. **后端托管缺口**：`127.0.0.1:3001` 在 Web 生产部署时不存在。上线前必须定托管方案（见 §3.4）。
2. **架构纪律**：33 个全局单例若缺事件总线纪律，易退化成「全局变量意大利面」（见 §4）。
3. **i18n 零基础**：未来出海无底座，后期改造贵（MVP 可暂不做）。
4. **测试无门槛**：252 个 .gd 仅靠 ad-hoc 脚本，系统越多回归风险越大（见 §5）。

## 3. 后端决策（核心）

### 3.1 决策结论
- **保留自建** Express + SQLite 后端（MVP / 单人开发最务实）。
- **Supabase 降为备用候选**（v2+ 再评估），不再是首选。
- 上线前必须解决托管：**规划 Docker 部署到轻量云**（本节仅规划，不实施）。

### 3.2 保留自建的理由
零外部账号 / 厂商锁定、可离线开发、迭代最快、数据模型自管、SQLite 单文件零运维。

### 3.3 Supabase 作为备用（何时切换）
- **触发条件**：不想自运维、需要托管 Auth / 实时订阅 / 对象存储时。
- **切换代价**：需重写 `APIManager` 适配 Supabase REST / Auth / RLS；用户与存档数据迁移；学习成本。
- **当前结论**：不推荐切换，保留为 v2+ 候选。

### 3.4 Docker 部署到轻量云（规划，不实施）
> ⚠️ 本节为**规划方案**，本阶段不落地。当前本地 `3001` 仅用于开发，不能用于生产。

**现状基础**：`backend/Dockerfile` 已存在（node:20-alpine，EXPOSE 3000，CMD `node src/server.js`，`SQLITE_PATH` 指向外部卷）；`migrations/` 目录已存在。

**目标拓扑**（单轻量云实例）：
```
[域名 / HTTPS]
      │
   Caddy（反向代理，自动证书，CORS 仅放行游戏域）
      │
   backend 容器（PORT=3000，SQLITE_PATH=/data/app.db）
      │
   volume: /data  ← sqlite 文件持久化 + 每日备份
```
Godot Web 静态资源可由同一 Caddy 或对象存储 / CDN 托管。

**轻量云选型**：1–2 vCPU / 2–4GB RAM / 40–60GB SSD，¥50–120/月（腾讯云 / 阿里云轻量应用服务器）。

**需补充的部署产物（规划清单）**：
- `docker-compose.yml`：backend 服务 + Caddy 服务 + `/data` 命名卷。
- 环境变量表：

| 变量 | 说明 | 示例 |
|---|---|---|
| `PORT` | 容器内监听端口 | `3000` |
| `SQLITE_PATH` | sqlite 文件绝对路径（卷内） | `/data/app.db` |
| `JWT_SECRET` | 令牌签名密钥（用 secrets 管理） | — |
| `CORS_ORIGIN` | 放行的前端域 | `https://game.example.com` |
| `MIGRATE` | 启动是否执行迁移 | `1` |

- **数据持久化与备份**：`/data` 挂卷；每日 cron 备份 `app.db` 到云存储（OSS / COS）；容器启动后执行 `migrations`。
- **安全**：`JWT_SECRET` 走密钥管理；CORS 仅放行游戏域；不将 3000 暴露公网；Caddy 自动 HTTPS。
- **CI/CD（规划）**：GitHub Actions 构建镜像 → 推镜像仓库 → 轻量云 pull 重启（可选 watchtower 自动更新）。
- **成本估算**：实例 ¥50–120/月 + 域名（Caddy 证书免费）。

## 4. 架构卫生（建议 4）

- **现状**：33 个 Autoload（含 7 事件总线），随功能演进自然膨胀。
- **模块分组建议**（仅约定，非立即重构）：

| 分组 | 典型成员 |
|---|---|
| core（基础设施） | 事件总线 ×7、配置、存档、SceneFramework |
| auth（账号） | AuthManager、SessionManager |
| content（内容） | 案件 / 线索 / 对话 / 知识库 / 推理墙 |
| ui（界面） | HUD、弹窗、设置、ToolBar |
| systems（系统） | 勋章、结局、时间线、工具、背包 |

- **依赖纪律**：跨模块只允许走 **7 事件总线**；禁止 autoload 之间硬调用（infra 层除外）。
- **命名澄清**：`SaveManager` 与 `SaveSystem` 同名易混，建议**合并或改名**（如统一为 `SaveSystem`），消除歧义。

## 5. 测试策略（建议 5）

- **现态**：无 GUT，仅 ad-hoc headless 脚本（`test_tool_system.gd`、`test_user_isolation.gd` 等）。
- **目标路径**：
  1. 先用现有 headless 脚本**固化回归**（接入本地 pre-push 或轻量 CI）。
  2. 按节奏引入 **GUT** 跑关键路径：存档 / 账号隔离 / 推理墙 / 工具系统。
  3. **不强行追 60% 覆盖**——以关键路径稳定为先。
- **建议**：将既有 headless 单测沉淀为 `tests/` 标准入口，逐步补 GUT。
