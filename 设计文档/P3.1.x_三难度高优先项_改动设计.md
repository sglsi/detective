# P3.1.x 三难度高优先项 · 改动设计

> 依据《验证_三难度模式运行机制.md》建议优先级（高）落地：
> **① 动态概率调整　② 困难隐藏提示选项　③ 竞技分数倍率**
> 其他设计项（误导概率 / 差异化提示文本 / 推理墙自动填充 / 检验次数 / 验证报告差异化 / 线索失效 / 凶手行动线 / 可信度展示）仍属更大扩展，**不在本范围**，见验证报告「缺失/偏差」表。

设计基线：`08_系统框架设计.md` §3.5（DifficultyManager 规范）、§8.2（影响矩阵，竞技难度 0.5×/1.0×/1.5×）、`00_核心设计思路.md` §2.3、`00_标准化开发目录.md` H-02（基础概率 0.7）、`福尔摩斯探案游戏GDD.md` §3 / §10.5。
核心原则不变：**难度不影响数据层，只影响「系统替玩家做了多少事」**。

## 二、① 动态概率调整（NORMAL）

### 框架
`difficulty_manager.gd` 新增常量与状态：
- `HINT_BASE_PROBABILITY = 0.7`（H-02 对齐 02 文档）
- `HINT_MAX_PROBABILITY = 0.95`（08 §3.5 天花板）
- `HINT_MIN_PROBABILITY = 0.1`（补充护栏，当前未直接用于下限；正常回落下限取 `HINT_BASE`）
- `hint_current_probability`（动态当前值，替代原 `hint_probability`）
- `_interactions_since_last_clue` + `STALL_INTERACTION_THRESHOLD = 15`
- `_wrong_inference_count` + `WRONG_INFERENCE_THRESHOLD = 3`

### 机制（对齐 08 §3.5 `on_progress_check`）
`should_show_hint()` 对 NORMAL 改用 `randf() < hint_current_probability`。
外部在「进度检查点」调用 `on_progress_check()`，按优先级判定：
1. 停滞（`_interactions_since_last_clue >= 15`）→ `+0.10`；
2. 否则连续错误推理（`_wrong_inference_count >= 3`）→ `+0.05`；
3. 否则正常进展 → `-0.05`，地板 `HINT_BASE`（0.7）。
调整后 `min(HINT_MAX, …)` 封顶，并发 `UIEventBus.hint_probability_adjusted` 信号（设计 §3.5 既有声明，本次在 `ui_event_bus.gd` **补建**该信号）。

### 运行时接线（调用点）
| 钩子 | 位置 | 作用 |
|------|------|------|
| `record_interaction()` | `DialogueManager.advance()` / `select_choice()` | 每次玩家推进/选择 = 一次交互，累加停滞计数 |
| `reset_stall_counter()` | `ClueSystem.collect_clue()`（去重更新与新增两路） | 发现线索即清零停滞计数 |
| `on_progress_check()` | `DialogueManager._end_dialogue()` | 每次对话结束 = 一个进度检查点，重算概率 |
| `record_wrong_inference()` / `reset_wrong_inference()` | （待推理墙稳定后接入 verdict 判定） | 错误推理计数 |

> 推理墙 verdict 接线留待推理墙系统稳定后接入（避免扰动未验证系统）；其余钩子已落地，`record_interaction` 阈值 15 保证普通节奏下不会频繁误触停滞。

## 三、② 困难隐藏提示选项

### 框架
- `DialogueNodeResource` 新增 `@export var is_hint_only: bool = false`（仅用于 choice 分支的引导/提示选项；正式推理分支**切勿**标记，否则困难模式会丢失该路径）。
- `DifficultyManager.filter_choices(nodes: Array) -> Array`：非 HARD 原样返回；HARD 剔除 `is_hint_only` 节点（对齐 08 §3.5 `filter_choices`）。

### 运行时接线
`DialogueManager._present_choices()`：先收集真实可显示分支节点，交 `DifficultyManager.filter_choices` 过滤，再组装 `choice_presented` 选项。
**安全护栏**：若所有分支均为提示选项且被 HARD 隐藏、且无 `end` 选项 → 退回首个原始 `next` 节点，避免选项面板空置卡死（与 `advance()` 空选项守卫同策略）。

---

## 四、③ 竞技分数倍率

### 框架
- `DifficultyManager.get_score_multiplier() -> float`：EASY 0.5 / NORMAL 1.0 / HARD 1.5（对齐 GDD §3 / 08 §3.9 `get_action_difficulty`）。
- `StarRatingSystem.get_adjusted_total_stars() -> int`：原始 `get_total_stars()` × 倍率，`roundi` 四舍五入。
- `StarRatingSystem.competitive_score: int`：在 `evaluate_badges()` 末尾写入 `get_adjusted_total_stars()`，使倍率**真实生效且可检视**（非死代码）。

### 设计取舍
- **徽章仍基于原始星级**（纯技巧，不因难度打折）；倍率仅作用于 `competitive_score` / 合成星级，供结局与排行等竞技场景消费。
- 结局系统当前引用 `get_case_total_stars()`（08 §8 文档方法，尚未实现），属独立缺口；本改动新增的 `get_adjusted_total_stars()` 即为其难度感知替代入口，后续结局/排行应消费之。

## 六、验证

### 回归单测（新增 `test_difficulty_enhanced.gd`）
1. 动态概率：NORMAL 基础 = 0.7；15 次交互 + `on_progress_check` → 0.8；反复触发封顶 0.95；重置后多次检查回落 0.7（下限）；3 次错误 → 0.75。
2. 困难隐藏提示：`[hint_only, real]` 经 `filter_choices`：HARD → 仅留 real（1 个）；NORMAL → 留 2 个。
3. 分数倍率：满星 9 × NORMAL = 9；6 星 × EASY = 3、× NORMAL = 6、× HARD = 9；`evaluate_badges` 后 `competitive_score` 随 HARD = 9。
