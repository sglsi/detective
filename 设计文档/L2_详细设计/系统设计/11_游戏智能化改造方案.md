## 0. 背景与目标

《谁是大侦探》推理墙在「困难模式」下要求玩家**自建**线索→推断→结论（自由文本 + 自连边）。
现有评价器 `WallBranchEvaluator` 把玩家图与 `case_branch_truth.gd` 里**作者写死的链**做逐项结构比对
（节点 id、`match_keys` 字面命中），正确率 = 命中 / max(玩家项数, 真相项数)。
困难模式玩家用的是自己的措辞与路径，id 不在真相表内 → 命中全 0 → 正确率崩到接近 0，
但 `wall_verify.gd` 又把标签写成「不判定对错」——**逻辑自相矛盾**，玩家实际看到"推理链正确率 20%"，评价体验失败。

本方案目标：
1. 让困难模式的评价**比对「案件事实/真相」而非「作者标准链」**，不同表述、不同路径推出同一真相应得高分。
2. 提供可落地的 **LLM 评审后端**实现路径。
3. 明确 **云端（VPS）部署游戏 + 后端**的可行性与容量边界。
4. 评估将同一后端扩展为**福尔摩斯对话智能体**（不止于评价）的可行性。

---

## 1. 困难模式评价的核心原则与四维模型

### 1.1 核心原则
评价对象 = **案件事实 / 真相**；不是作者写的那条标准链。
作者链只是真相的一种表达；玩家用不同词、不同中间步推出同一正确结论，理应高分。

### 1.2 四维评价模型（权重）

| 维度 | 权重 | 测什么 | 计算方式（不依赖作者链） |
|------|------|--------|--------------------------|
| 结构有效性 | 20% | 图是不是"好推理的形状" | 每条推断≥1 证据、每条结论≥1 推断、无悬空/反向错乱、有终局结论节点 |
| 证据引用 | 25% | 是否真用了已收集线索 | 已收集线索被引用占比 × 引用相关性 |
| **结论正确性** | **35%** | 终局结论是否指向真相 | 终局节点语义是否映射到 canonical 真相结果（谁干的/发生了什么） |
| 步骤合理性 | 20% | 每步推导是否站得住 | 经概念标注后，玩家边是否对应"有效推理规则"（见 2. / 3.） |

**硬门槛**：`结论正确性 == false` 时，星级封顶 2 星（避免推错人还能满星）。

## 2. Track A（无 LLM，离线，可进当前 Web 构建）

- 从 `case_branch_truth` / `reasoning_chains` 的 `match_keys` + `subject`/`object` 抽取**每案概念词典**（含同义词）。
- **概念标注器**：把玩家每个自由节点文本映射到最近的 canonical 概念（关键词/同义词命中）。
- 把 `Truth.branches()` 的边转成**"有效推理规则库"**（前提概念→结论概念）。玩家每条边经标注后查规则库：有效→得分；矛盾/无关→低分。
- 终局节点映射到真相结果做"结论正确性"判定。
- 局限：同义词覆盖度决定上限，需每案补词典；完全离线、确定性强、零成本。

## 3. Track B（LLM 评审后端 · 详细方案）

> ⚠️ **重大修订（2026-09-10）**：经核查，`backend/` 已存在完整 Express 后端
> （`backend/src/server.js`，含 auth/saves/progress/editor 路由、CORS `*`、速率限制、Supabase、Dockerfile、`docker-compose.yml`），
> Godot 客户端已通过 HTTP/JSON 与它通信（见 `communication_protocol.md`）。
> 因此 **eval 不应另起 Python 服务**，而是**在现有 Express 后端新增路由**，随现有 Docker 一起上云。

### 3.1 架构

```
┌──────────────┐  POST /api/evaluate (JSON)  ┌──────────────────────────┐
│ Godot Web    │ ───────────────────────────▶ │ Express 后端 (现有)       │
│ (wall_verify)│ ◀─────────────────────────── │ + 新增 routes/evaluate   │
│  HARD 提交时 │   200 {四维分数+理由}          │ + routes/agent (见 §5)   │
└──────────────┘                             └───────────┬──────────────┘
                                                       │ OpenAI 兼容 API
                                                       ▼
                                              ┌──────────────────────┐
                                              │ LLM (云端 / 本地Ollama)│
                                              └──────────────────────┘
```

### 3.2 新增文件（在 backend/ 内）

| 文件 | 职责 |
|------|------|
| `src/routes/evaluate.js` | 暴露 `POST /api/evaluate`，校验载荷、调 LLM、缓存、返回结构化 JSON |
| `src/lib/llmClient.js` | 封装 LLM 调用（OpenAI 兼容 / 本地 Ollama），读环境变量，限时，JSON 模式 |
| `src/lib/conceptIndex.js` | （可选）Track A 概念词典与标注，作为无 LLM 时的降级路径 |
| `src/lib/evalCache.js` | 内存 + 可选文件缓存，key = hash(case_id+difficulty+规范化玩家图) |
| `.env.example` 增补 | `EVAL_API_BASE` / `EVAL_API_KEY` / `EVAL_MODEL` |

在 `server.js` 注册：`app.use('/api/evaluate', evaluateRoutes)`。

### 3.3 服务端实现要点

- **CORS**：现有 `cors({origin:'*'})` 已覆盖，无需改动。
- **认证**：复用现有 JWT / `X-Guest-ID` 机制（`communication_protocol.md` §3）。
- **速率限制**：现有 `/api/` 全局 200 次/15min；eval 为重量级调用，建议单独加
  `rateLimit({windowMs:60000, max:10})` 防止 LLM 被刷爆。
- **LLM 调用（stdlib-free，用 axios/fetch）**：
  - `EVAL_API_BASE` 默认 `https://api.openai.com/v1`；本地填 `http://localhost:11434/v1`（Ollama，免 key、离线）。
  - `response_format={type:"json_object"}` 强制 JSON 输出 + 严格 system 约束。
  - `timeout: 60000`。
- **缓存**：相同提交直接返回，不重复调 LLM；可落 `eval_cache.json` 跨重启复用。
- **降级**：LLM 超时/非 200/JSON 解析失败 → 返回 `{error:"eval_unavailable"}`，客户端降级到 Track A 或定性反馈。

### 3.4 Prompt 模板（质量关键）

**System**：
```
你是《谁是大侦探》推理游戏的评审。评估玩家在【困难模式】自建的推理链。
铁律：
- 评的是推理质量与对真相的契合度，不是与任何"标准答案文本"的字面相似度。
- 玩家用不同措辞、不同中间步骤推出同一正确结论，应得高分。
- 只依据下方"案件线索"与"案件真相"评判，不引入外部知识。
按四维打分（各 0.0~1.0）：①结构有效性 ②证据引用 ③结论正确性(最关键) ④步骤合理性。
只输出 JSON，不要任何解释文字。
```

**User**（客户端拼装）：案件ID、案件真相摘要（`case_branch_truth.derive_truth`）、已收集线索（id+name+描述）、
玩家图（节点[类型+文本] + 边[from→to, kind]）。要求输出：
```json
{
  "structure": 0.0, "evidence": 0.0, "conclusion": 0.0, "step_soundness": 0.0,
  "conclusion_correct": true,
  "reasons": {"structure":"", "evidence":"", "conclusion":"", "step_soundness":""},
  "comment": "一句话总评"
}
```

### 3.5 Godot 客户端改造（`scripts/clue/wall/wall_verify.gd`）

1. `_open_verify_result()` 中 HARD 难度：立即锁墙（`_verified=true`、`_graph_view._editable=false`），
   显示"评委评审中…"spinner（复用 `VerifyBackdrop`）。
2. 组装 payload：从 `ClueSystem` 取已收集线索、`case_branch_truth.derive_truth(_scene_id)` 取真相、
   从 `owner._relations`/`graph_nodes`/`derived_conclusions` 取玩家图。
3. `HTTPRequest.request(EVAL_URL, headers, POST, json)`；
   `EVAL_URL` 取 `OS.get_environment("EVAL_URL")` 或常量 `http://localhost:3000/api/evaluate`（生产改为 `https://api.sherlock-game.com/api/evaluate`）。
4. `_on_eval_completed`：成功 → `final = 0.20*structure+0.25*evidence+0.35*conclusion+0.20*step_soundness`，
   写进 `_last_report`（替换"正确率 X%"）；失败/超时 → 降级到 Track A 定性反馈（参考 `auth_panel.gd:170` 看门狗思路，超时强走降级，防永久转圈）。
5. **客户端改动进了 pck，必须重导出 Web 构建 + 注入新戳**（与历次改动一致）。

### 3.6 测试步骤
1. `curl -X POST localhost:3000/api/evaluate -d @sample.json` → 校验 JSON 结构与 CORS。
2. 连发相同请求 → 日志 `cache hit`、未调 LLM。
3. headless Godot `test_eval_hard.gd`：构造 HARD 图，断言收到分数 + 报告生成。
4. 关掉 key 提交 → 断言降级分支、不卡死。

## 4. 云端（VPS）部署：游戏 + 后端 + eval

### 4.1 可行性结论：**完全可行，且已有部署骨架**
- 游戏本体是 **Godot WebGL 静态资源**（`web_build/`），由任意静态服务器（nginx / 现有 `serve_web.py`）托管。
- 后端是 **Express + Docker**（`backend/Dockerfile`、`docker-compose.yml`），天然适合 VPS 容器化。
- 二者同域部署：nginx 托管静态资源 + 反向代理 `/api` 到 Node 容器。Godot 的 `HTTPRequest` 已验证可用。
- LLM 调用从 Node 出网到 OpenAI/Ollama，key 仅存服务端，客户端永不可见。

### 4.2 推荐部署拓扑
```
[用户浏览器] ──HTTPS──▶ [VPS: nginx]
                             ├─ 静态: /  → web_build/ (Godot WebGL)
                             └─ /api → proxy_pass → [Node 容器 :3000]
                                                  └─▶ LLM (OpenAI / 本地Ollama)
[持久化] SQLite(命名卷) 或 Supabase(已集成)
```
- HTTPS：Let's Encrypt 免费证书（Godot WebGL 在 https 下运行无碍）。
- 现有 `docker-compose.yml` 已规划 `SQLITE_PATH=/data/local_dev.db` 命名卷持久化。

### 4.3 容量评估（最大支持用户数）
- **游戏静态资源**：客户端在浏览器本地跑 WebGL，服务端仅提供一次性下载 + 偶发 API 调用。
  一台 2–4 vCPU / 4–8GB 的 VPS 用 nginx 可轻松支撑**数百到数千并发**玩家（瓶颈在带宽，不在算力）。
- **瓶颈在 LLM 评审调用**：每次 `/evaluate` 是一次数秒的 LLM 请求。
  - 单 Node 进程 + 连接池，约可并行 5–20 个 eval 请求 → 约 100–600 次评审/小时（取决于模型延迟）。
  - 玩家一局通常只提交数次评审 → **数百并发玩家、零星评审**毫无压力。
  - 硬上限 = LLM 厂商 RPM/TPM 配额 + VPS 算力。OpenAI 低档配额即可支撑中小规模。
- **扩容路径**：Node 多副本 + 负载均衡；评审换更快/本地 GPU(Ollama) 模型；eval 结果缓存去重。

> 估算小结：小 VPS（2–4 vCPU/4–8GB）稳态支撑 **约 200–500 并发玩家**；规模化需横向扩展 Node + 提升 LLM 配额。属典型轻量 Web 游戏负载，远未触及上限。

### 4.4 成功范例（同类架构已被验证）
- **AI Dungeon / NovelAI**：LLM 驱动的叙事游戏，云端 Express/Python 后端 + 前端，日活百万级，证明"游戏+LLM 后端"模式成熟。
- **LLM-as-a-Judge**：LMSYS Chatbot Arena 等用 LLM 当评委打分，是成熟的 ML 评测范式，与本方案"LLM 评审推理链"同构。
- **探案/推理类 + LLM**：社区已有大量"谋杀之谜""侦探 NPC"用 GPT 实现动态对话与评审的实验。
- **Godot WebGL 云端托管**：itch.io / 自建 VPS 部署 Godot Web 游戏是常见做法。
> 注：与本作"完全相同的游戏"范例罕见，但**架构模式（Web 游戏 + LLM 后端 + 容器化部署）已被广泛成功验证**。

## 5. 扩展：福尔摩斯对话智能体（eval 不止于评价）

### 5.1 可行性：**完全可行，且是同一后端的自然延伸**
新增 `POST /api/agent/chat` 路由，与 eval 共享 LLM 客户端与鉴权。

### 5.2 设计
- **Persona System Prompt**：福尔摩斯人格 + 当前案件状态（场景、已收集线索、进度）+ 对话历史（每玩家独立 session）+ 约束：
  - 只说逻辑上可推得的内容，绝不剧透真相；
  - 保持人设（敏锐、略傲慢、引经据典）；
  - 可引导玩家思考，但不直接给答案。
- **Session 记忆**：每玩家一个会话（Redis 或 Supabase），保存历史轮次供上下文。
- **客户端**：Godot 对话 UI 发 `utterance + session_id`，后端流式/整段返回 Holmes 回复。
- **可衔接评价**：智能体可在玩家卡住时提示"你的推理链缺了哪类证据"，形成"引导—提交—评审"闭环。

### 5.3 注意事项
- **延迟**：LLM 生成需流式（SSE）以免长时间等待；可在客户端显示"福尔摩斯正在思考…"。
- **成本/配额**：对话比评审更频繁，需更激进的缓存与更便宜的模型。
- **一致性/安全**：用 system 约束防人设崩坏；防玩家 prompt injection（不执行玩家输入中的指令）。
- **降级**：LLM 不可用时回退到现有脚本化对话。

## 6. 知识层与模型积累策略：OpenAI 兼容 vs 本地 Ollama

> 本节约答一个常见误解：**"用 OpenAI key 时 LLM 怎么积累游戏知识？本地 Ollama 是不是能学云服务器文档形成自有知识库？"**

### 6.1 必须先澄清的误解
两种方案都**不会"自动"从游戏里学到知识**。模型权重不会因为你调用了它就改变。游戏专属知识必须靠你主动喂入，而这只有两条本质不同的路径：

- **路径 A：每次请求时注入**（System Prompt + RAG 检索 + 工具/函数定义）。知识来自本次请求内容，模型本身不被修改，调用结束即忘。**OpenAI 兼容 与 Ollama 在此路径上能力完全一样**——知识由你的代码侧提供，不是模型自带。
- **路径 B：持久化沉淀进权重**（微调 / LoRA / 继续预训练）。这才是"积累并完善知识库、规则库"的唯一真实形态，两者差异巨大（见 6.2 / 6.3）。

### 6.2 用 OpenAI 兼容 key：知识如何积累
不会自动积累。你要做的是：把游戏结构化知识（案真相、规则库、推理链、设计文档）整理成语料 → 要么**每次用 RAG 检索注入**（推荐，即时生效、可更新），要么**周期性提交微调任务**把知识烤进一个托管模型。
- **API 本身不会"记住"你的游戏**；跨调用不自动累积，得你手动跑微调任务。
- 微调得到的权重在厂商服务器上、**你不拥有、不能下载**；推理按 token 计费更高。
- 知识积累的责任完全在你：维护语料库 + 触发训练任务。

### 6.3 用本地 Ollama：优势与前提
有真实优势，但前提是**你愿意建一条训练闭环**：
- 可对你服务器上的开放权重模型做 LoRA / 继续预训练，适配器权重就在云服务器本地，**可反复迭代、数据不出域、边际成本≈0**（只要 GPU 在）。
- 闭环示意：
  ```
  游戏文档 + 程序流程 + 玩家交互日志 + eval 结果
        │  (你建的管道，非模型自带)
        ▼
  自动生成训练数据 → 在服务器训 LoRA → 同机部署 → 新数据回流再训
  ```
- **Ollama 不会"自己学习"文件**——这个闭环是你搭的管道；但相比 OpenAI 托管，本地能真正做到"知识沉淀在自家服务器、可迭代、隐私留存"。
- 代价：需要 GPU 与一定 ML 工程能力；7B–70B 本地模型在复杂推理/人设扮演上通常弱于前沿强模型，除非重度微调。

### 6.4 对本案的贴切结论
1. **知识源已在你仓库里**：`case_branch_truth.gd` / `reasoning_chains.gd` / 本系列设计文档本身就是结构化知识。两种方案第一步都一样——建一个**检索/RAG 层 + 显式规则注入**，把知识喂给模型，而非纠结选哪家。
2. **规则库别交给 LLM「凭记忆」**：困难模式"四维评价"本质是确定性代码，应永远由代码侧做确定性校验 + 在 prompt 里显式给规则文本，而不是让 LLM 自己回忆规则。这是 §0 所述"正确率崩 0"同源教训的延续——别再让模型去比对它记不住的作者链。
3. **务实路线**：
   - 开发/上线期用 **OpenAI 兼容强模型**做福尔摩斯智能体与困难模式 LLM 评审，质量最稳、出活最快，知识全靠 prompt/RAG 注入；
   - 想要**数据不出域 / 边际零成本 / 可迭代自训**时，在云服务器跑 **Ollama + Qwen2.5-72B / Llama-70B** 接同一套 RAG，并可选把文档+eval 结果做成 LoRA 闭环；
   - **混合架构最稳**：强模型保质量，本地模型降本/保隐私。

### 6.5 一句话回答"选哪家"
"积累知识"在"每次注入"层面两家无差异（必做前提，与选型无关）；在"训进权重"层面 Ollama 有真实优势（自有、可迭代、隐私），但前提是建训练管道；而无论选谁，**游戏的确定性规则都不该交给 LLM 记忆，必须由代码 + 显式规则文本兜底**。

## 7. 落地路线与待确认项

| 阶段 | 内容 | 依赖 |
|------|------|------|
| Phase 0 | 困难模式不再显示"正确率 vs 作者链"，改定性反馈；理顺 `wall_verify` 自相矛盾 | 无 |
