## 1. 困难模式评价的核心原则与四维模型

### 1.1 核心原则（已落地）
评价对象 = **案件事实 / 真相**；不是作者写的那条标准链。
作者链只是真相的一种表达；玩家用不同词、不同中间步推出同一正确结论，理应高分。

### 1.2 四维评价模型（权重）— **已按此实现**

| 维度 | 权重 | 测什么 | 实际计算方式 |
|------|------|--------|--------------------------|
| 结构有效性 | 20% | 图是不是"好推理的形状" | `connectivity*0.6 + progression*0.4`（连通性 + 递进性） |
| 证据引用 | 25% | 是否真用了已收集线索 | 有证据支撑的产出项占比 |
| **结论正确性** | **35%** | 终局结论是否指向真相 | `conclusion_matcher` 宽容匹配（阈值 0.45）+ 核心结论 id 命中 |
| 步骤合理性 | 20% | 每步推导是否站得住 | `connectivity*0.8 + (1-contra_ratio)*0.2`（矛盾率惩罚） |

**硬门槛（已实现）**：`结论正确性 == false` 时星级封顶 2 星（`if not conclusion_correct` 分支）。

### 1.3 已知局限与增强方向

| 局限 | 影响 | 增强方向 |
|---|---|---|
| 概念/同义词词典覆盖面决定上限 | 玩家用新鲜措辞可能误判 | ①扩词典（每案维护）②引入 LLM 语义判定（§3） |
| 结论匹配靠 id 别名 + 文本相似度 | 高度概括或隐喻式结论可能漏判 | LLM 判定"结论是否指向真相"，与确定性结果取交集 |
| 纯客户端、无数据回流 | 无法分析玩家真实困难、无法迭代 | 打通 §3.5 上报链路 |
| 无个性化反馈 | 报告只有分数与要点 | LLM 生成"缺哪类证据"的引导语（可复用 §5 智能体） |

## 2. Track A（无 LLM，离线）— **已完成**

实际落地形态：

- 从 `case_branch_truth` / `reasoning_chains` 抽取真相分支与核心结论集合（`_core_conclusion_ids`）。
- `conclusion_matcher.gd` 做**结论文本宽容匹配**（归一化 + 相似度，阈值 0.45），供评价器与图控制器共用。
- 玩家自由节点（`note_conclusion_*` / `note_hypo_*`）被识别并纳入图结构统计。
- 四维分数 + 星级 + 理由 + 一句话总评全部在客户端确定性计算完成。

**优点**：完全离线、确定性、零成本、无延迟，已可直接进 Web 构建。
**局限**：同义词/措辞覆盖度决定上限；需每案补词典；无法给出个性化引导。

## 4. 云端（VPS）部署：游戏 + 后端 + eval

### 4.1 可行性结论：**可行，部署骨架已存在**
- 游戏本体是 **Godot WebGL 静态资源**（`web_build/`），由静态服务器托管（仓库根 `serve_web.py` 可用于本地/内网，生产建议 nginx）。
- 后端是 **Express + Docker**：`backend/Dockerfile` 存在，**`docker-compose.yml` 在仓库根目录**（不在 `backend/`）。
- 二者同域部署：nginx 托管静态资源 + 反向代理 `/api` 到 Node 容器。Godot 的 `HTTPRequest` 已验证可用。
- LLM 调用从 Node 出网到 OpenAI/Ollama，key 仅存服务端，客户端永不可见。

### 4.2 推荐部署拓扑
```
[用户浏览器] ──HTTPS──▶ [VPS: nginx]
                             ├─ 静态: /  → web_build/ (Godot WebGL)
                             └─ /api → proxy_pass → [Node 容器 :3000 容器内]
                                                  └─▶ LLM (OpenAI / 本地Ollama)
[持久化] Supabase(已集成) 或 SQLite
```
- 容器内端口默认 3000（`server.js` 的 `process.env.PORT || 3000`）；
  **本机开发实际用 3001**（3000 被系统服务占用），部署时用 env 统一即可，不必改代码。
- HTTPS：Let's Encrypt 免费证书。
- 现有 `storage.js` / `supabase.js` / `migrate.js`（`backend/src/db/`）已提供存储层。

### 4.3 容量评估（最大支持用户数）
- **游戏静态资源**：客户端浏览器本地跑 WebGL，服务端仅一次性下载 + 偶发 API 调用。
  2–4 vCPU / 4–8GB 的 VPS 用 nginx 可支撑**数百到数千并发**玩家（瓶颈在带宽，不在算力）。
- **瓶颈在 LLM 评审调用**：每次 `/evaluate` 是数秒的 LLM 请求。
  - 单 Node 进程约可并行 5–20 个 eval 请求 → 约 100–600 次评审/小时。
  - 玩家一局通常只提交数次评审 → **数百并发玩家、零星评审**毫无压力。
  - 硬上限 = LLM 厂商 RPM/TPM 配额 + VPS 算力。
- **扩容路径**：Node 多副本 + 负载均衡；评审换更快/本地 GPU(Ollama) 模型；eval 结果缓存去重。

> 估算小结：小 VPS（2–4 vCPU/4–8GB）稳态支撑 **约 200–500 并发玩家**；规模化需横向扩展 Node + 提升 LLM 配额。

### 4.4 成功范例（同类架构已被验证）
- **AI Dungeon / NovelAI**：LLM 驱动的叙事游戏，云端后端 + 前端，证明"游戏+LLM 后端"模式成熟。
- **LLM-as-a-Judge**：LMSYS Chatbot Arena 等用 LLM 当评委打分，与本方案"LLM 评审推理链"同构。
- **Godot WebGL 云端托管**：itch.io / 自建 VPS 部署 Godot Web 游戏是常见做法。
> 注：与本作"完全相同的游戏"范例罕见，但**架构模式（Web 游戏 + LLM 后端 + 容器化部署）已被广泛成功验证**。

## 5. 扩展：福尔摩斯对话智能体（eval 不止于评价）

### 5.1 可行性：**完全可行，是同一后端的自然延伸**
新增 `POST /api/agent/chat` 路由，与 eval 共享 LLM 客户端与鉴权。**当前未开始**。

### 5.2 设计
- **Persona System Prompt**：福尔摩斯人格 + 当前案件状态（场景、已收集线索、进度）+ 对话历史（每玩家独立 session）+ 约束：
  - 只说逻辑上可推得的内容，绝不剧透真相；
  - 保持人设（敏锐、略傲慢、引经据典）；
  - 可引导玩家思考，但不直接给答案。
- **Session 记忆**：每玩家一个会话（Redis 或 Supabase），保存历史轮次供上下文。
- **客户端**：Godot 对话 UI 发 `utterance + session_id`，后端流式/整段返回 Holmes 回复。
- **可衔接评价**：智能体可在玩家卡住时提示"你的推理链缺了哪类证据"，形成"引导—提交—评审"闭环。
  （对应 §3.4 输出中的 `guidance` 字段，两者可共用一套生成逻辑。）

### 5.3 注意事项
- **延迟**：LLM 生成需流式（SSE）以免长时间等待；客户端显示"福尔摩斯正在思考…"。
- **成本/配额**：对话比评审更频繁，需更激进的缓存与更便宜的模型。
- **一致性/安全**：用 system 约束防人设崩坏；防玩家 prompt injection。
- **降级**：LLM 不可用时回退到现有脚本化对话（当前对话系统完全脚本化，天然可回退）。

## 6. 知识层与模型积累策略：OpenAI 兼容 vs 本地 Ollama

> 本节约答一个常见误解：**"用 OpenAI key 时 LLM 怎么积累游戏知识？本地 Ollama 是不是能学云服务器文档形成自有知识库？"**

### 6.1 必须先澄清的误解
两种方案都**不会"自动"从游戏里学到知识**。模型权重不会因为你调用了它就改变。游戏专属知识必须靠你主动喂入，而这只有两条本质不同的路径：

- **路径 A：每次请求时注入**（System Prompt + RAG 检索 + 工具/函数定义）。知识来自本次请求内容，模型本身不被修改，调用结束即忘。**OpenAI 兼容 与 Ollama 在此路径上能力完全一样**。
- **路径 B：持久化沉淀进权重**（微调 / LoRA / 继续预训练）。这才是"积累并完善知识库"的唯一真实形态。

### 6.2 用 OpenAI 兼容 key
不会自动积累。你要做的是：把游戏结构化知识整理成语料 → 要么**每次用 RAG 检索注入**（推荐），要么**周期性提交微调任务**。
- **API 本身不会"记住"你的游戏**；跨调用不自动累积。
- 微调得到的权重在厂商服务器上、**你不拥有、不能下载**；推理按 token 计费更高。

### 6.3 用本地 Ollama：优势与前提
有真实优势，但前提是**你愿意建一条训练闭环**：
- 可对开放权重模型做 LoRA / 继续预训练，适配器权重就在本地，**可反复迭代、数据不出域、边际成本≈0**（只要 GPU 在）。
- 闭环示意：
  ```
  游戏文档 + 程序流程 + 玩家交互日志 + eval 结果
        │  (你建的管道，非模型自带)
        ▼
  自动生成训练数据 → 在服务器训 LoRA → 同机部署 → 新数据回流再训
  ```
- **Ollama 不会"自己学习"文件**——这个闭环是你搭的管道。
- 代价：需要 GPU 与 ML 工程能力；7B–70B 本地模型在复杂推理/人设扮演上通常弱于前沿强模型。

### 6.4 对本案的贴切结论
1. **知识源已在你仓库里**：`data/case_branch_truth.gd` / `data/reasoning_chains.gd` / 本系列设计文档本身就是结构化知识。两种方案第一步都一样——建**检索/RAG 层 + 显式规则注入**。
2. **规则库别交给 LLM「凭记忆」**：困难模式"四维评价"本质是确定性代码（**且已在客户端实现**），
   应永远由代码侧做确定性校验 + 在 prompt 里显式给规则文本。LLM 只用来补语义漏判，不做主裁判。
   ——这是 §0 所述"正确率崩 0"同源教训的延续。
3. **务实路线**：
   - 开发/上线期用 **OpenAI 兼容强模型**做智能体与语义校正，质量最稳、出活最快；
   - 想要**数据不出域 / 边际零成本 / 可迭代自训**时，跑 **Ollama + Qwen2.5-72B / Llama-70B** 接同一套 RAG；
   - **混合架构最稳**：强模型保质量，本地模型降本/保隐私。

### 6.5 一句话回答"选哪家"
"积累知识"在"每次注入"层面两家无差异（必做前提，与选型无关）；在"训进权重"层面 Ollama 有真实优势；
而无论选谁，**游戏的确定性规则都不该交给 LLM 记忆，必须由代码 + 显式规则文本兜底**。
