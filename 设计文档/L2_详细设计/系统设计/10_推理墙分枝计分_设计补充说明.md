## 1. 背景与要解决的问题

原评价体系（v4.0 三维离散制）的**推理之星**只看「玩家有没有连边」：

- `_state_ctl._support_signals() >= 3` → `VERIFIED`（已获证实）
- `_state_ctl._support_signals() >= 1` → `SUPPORTED`

**根因**：它数的是「关系数量」而非「关系对错」。玩家只要在推理墙上随手连几条边（哪怕是错的），
推理之星就能给高分，四档判定也能到「已获证实」。**这会鼓励玩家乱选**——只要推理系统有选择关系，
无论对错都给好评。这就是用户反馈的「只要推理系统有选择关系，评价体系就会给出好的评价」。

本次重构目标：**评分必须看「推理链整体对错」**，连错的东西一样进分母，连得越滥正确率越低。

## 3. 计分公式（用户第 4 点，加一处修正）

对每条**玩家动过的链**（至少建了属于它的一个节点或一条边）：

- `T` = 真相项数（该链**玩家可产出的**节点数 + 边数）
  - ⚠️ **线索(clue)与人物(person)不计入 T**：线索是观察得来、墙上预置，人物由 `related_npcs` 自动派生，
    玩家都无法在推理墙里「产出」它们；是否用对了体现在**边**上（连对 `c201→H2-01` 才算用到 `c201`）。
    若把线索也算进 T，则 B 永远小于 T，完美解永远到不了 100%（初版实测卡在 67.8%）。
- `B` = 玩家在该链内建的项数（节点 + 边，**含错误边**）
- `H` = 其中命中真相的项（逐项 **0 / 0.5 / 1** 计分：完全命中=1，两端对方向反=0.5，未命中=0）
- **`R_b = H / max(B, T)`**

全案汇总：

- `S = Σ H`，`S_max = Σ max(B, T)`，**`R = S / S_max`**

### 关于 max(B, T) 的说明（这是本设计相对用户原话的唯一一处修正）

用户原话是「分母为这个分枝中的节点、边关系的总和（连的越多分母越大）」，即只用 `B`。
但纯用 `B` 会出一个漏洞：**玩家只连 1 条对的边 = 1/1 = 100% 三星**，比全连对还高。
取 `max(B, T)` 等价于**同时看精度与覆盖率**，仍是单一公式、一句话讲得清，且完美解恰好 = 100%。

## 4. 两个必须补的洞

### 洞 1：只做最短一条链就能三星

玩家把 CH02 马车印迹（链短）做到完美，其余 13 条不碰 → R=100%。
**补法**：标 **core 链（破案必经，8 条：CH02/03/04/05/07/09D/09E/09F）**，
**未激活的 core 链按 R=0 计入分母**；其余 optional 链激活才算、做砸不拖分（保住「错误无惩罚」）。

### 洞 2：误导项怎么算分

真相里把陷阱节点标 `misleads: [{id, expect:"negate"}]`（玩家应**否定**它）：

- 玩家**否定**它（建 oppose 边）→ 命中，+1 分（奖励识破，并加成洞察星）
- 玩家**采纳**（主动产出该节点 / 对它建 support 边）→ 0 分，且**三星硬条件直接失败**（封顶 2⭐）
- 玩家没碰 → 不计入分子分母，不奖不罚

## 5. 星级阈值与四档判定（思傅裁定）

| 比值 R | 星级 | 四档 verdict |
|---|---|---|
| R ≥ 80% | ★★★ | VERIFIED（已获证实） |
| R ≥ 55% | ★★ | SUPPORTED（倾向成立） |
| R ≥ 25% | ★ | INSUFFICIENT（证据不足） |
| R < 25% | — | INSUFFICIENT（尚未形成有效推理） |
| 矛盾边 / 采纳误导项 且 R<80% | — | CONTRADICTORY（矛盾冲突） |

> **保留独立的矛盾语义**：存在矛盾边或采纳误导项时，即使正确率不低也判「矛盾冲突」，
> 不与「已获证实」混淆。

**阈值变化**：用户将原 90/60/30 改为 **80/55/25**（更贴合 14 链、每链项数不一的实际分布）。

## 7. 评分只基于「玩家真实关系」

引擎输入来自 `GraphViewController.snapshot_player_work()`：

- `relations`：玩家拖拽建的真实关系（`_relations`），**绝不掺入 `_derive_edges()` 自动派生的数据预设边**
  （否则玩家什么都不做也满分）
- `graph_nodes`：画布上玩家节点（kind=hypo 的采纳/自建推断；`note_*` 自造节点不计节点分）
- `derived_conclusions`：玩家落盘结论
- 虚线（dashed，存疑）边只显示不判定、也不计分

**归属规则**（杜绝跨链公共节点重复计分）：按 branches 顺序两轮认领——
① 双端都在链内者精确归属；② 只有一端在链内者兜底认领（链外乱连照样进分母、0 分）。
不允许一轮「单端即认领」，否则 `c309`（同属 CH03/CH05）会被错误抢链，完美解到不了 100%。

## 8. 数据结构

- `data/case_branch_truth.gd`：`branches()` 返回 14 条链真相（节点 + 边 + 误导项）。
  **只引 id，不重复录文本**——节点文本仍由各 `sceneN.gd` 的 `reasoning_hypothesis()` 提供，
  经 `CaseReasoningRegistry` 聚合，避免两处维护漂移。尚未在 sceneN 落地的 id 属「预留」，
  引擎查不到时按「未建」处理，安全。
- `scripts/clue/wall_branch_evaluator.gd`：纯数据引擎（不依赖场景树），可 headless 单测。
- `autoload/star_rating_system.gd`：新增 `case_branch_log`（场景→推理链明细缓存），供场景八结论面板。
- 结论节点 id 归一化：画布上形如 `conclusion_CL3-1`，真相表写裸 `CL3-1`，由 `_norm()` 双向归一。

## 9. 验证窗口与场景八结论面板

- **验证窗口（每场景提交验证时）**：标题显示四档 verdict；下方一行显示三维三星（🔍🧠💡）；
  再下一行显示一句话总结（`WallBranchEvaluator._summary()`，如「推理链完整闭合」「尚有缺口」）。
  **不列出逐条对错**。
- **场景八全案总结（`_show_scene_rating(show_case_total=true)`）**：除原有各链三维星概览外，
  额外遍历 `StarRatingSystem.case_branch_log`，逐条列出「✅/⚠️/❌ 链名 正确率%（星级）」，
  即把整案的「结论」一次性告诉玩家，鼓励重玩。
