## 0. 结论摘要

**诊断一句话**：推理墙当前的定位是「评分器 + 图谱容器」，不是「推理进程的驱动力」——
玩家推理得再好或再糟，剧情路径一模一样（`detective_scene.gd:531-533` 无条件推进）；
墙内全部过程数据（逐链命中率、缺失节点/边、误导采纳）都在生产，但只被场景八结局面板消费一次。

**方案一句话**：按「剧情与推理墙松耦合」总纲（用户裁定），墙只写账本、剧情只读账本——
verdict 不决定「是否推进」（推进逻辑保持不动，永不卡死），只决定「推进后走哪条内容路径」：
正确推理引导主线，被误导的推理引导旁支剧情，旁支行不通时能「返回」主线继续，错误永不阻断游戏。

**实施顺序**：Phase 0 口径统一（T 按已收集线索裁剪 + 图谱写色切同一评分源）→
Phase 1 正式链先修后搬 → Phase 2 进程可视化 → Phase 3 里程碑 gate 化 + 案件进程轴 →
Phase 4 剧情挂载（旁支剧情）。前三阶段零剧情风险，Phase 4 需内容生产。

## 1. 现状设计思想复原

### 1.1 三层架构（06_推理墙运行机制.md）

| 层 | 内容 | 落地状态 |
|---|---|---|
| 核心基础层 | 线索库、推理看板、四级验证体系、结论里程碑 | ✅ 全部落地 |
| 扩展进阶层 | 可信度评估、矛盾疑点册、**案件进度轴** | 前两者落地；**进度轴 §3.3 M2+ 未实现** |
| 全局支撑层 | 三星评价、难度适配、存档、统计 | ✅ 落地 |

### 1.2 四层节点模型与回溯推理

玩家在画布上把 线索(clue) → 推断(hypo) → 结论(concl) → 人物(person) 连成图谱，
提交验证时与「作者链」（真相表）逐项比对。边 kind：support / oppose / contradict / target；
画布结论带 `conclusion_` 前缀，真相表写裸 id，`norm()` 双向归一。

真相表来源：`case_branch_truth.gd branches()` 分流——链库覆盖的 id 用 `ReasoningChains.derive_truth()`
从 gate 字段机械派生，其余走 `_legacy_branches()` 手工表。当前链库仅覆盖 2 条练习链（CH01W/CH01M）。

### 1.3 计分口径与四档判定（10 号文档）

- 单链 `R_b = H / max(B, T)`：H=命中（精确 1.0 / 方向反 0.5 / 采纳误导 0），B=玩家建项（错边进分母），
  T=真相项（**只计玩家可产出的 hypo/concl 节点** + 全部真相边；共享节点按「首条链认领」去重）。
- 全案 `R = ΣH / Σmax(B,T)`；两轮归属认领（双端在链内优先，单端兜底进分母 0 分）。
- 四档判定：`R≥0.80 → VERIFIED(3)` / `≥0.55 → SUPPORTED(2)` / `≥0.25 → INSUFFICIENT(1)` /
  有 contradict/oppose 边或采纳误导 → `CONTRADICTORY(0)`（hard_fail）。
- 四档与三维星级（观察星=线索收集、推理星=链 R、洞察星=合成层 ratio）**共用同一评分源**
  `wall_state._evaluate_branch()`；困难模式分流 `HardModeEvaluator`（四维定性 35/25/20/20）。
- 误导项 `expect:"negate"`：采纳（主动产出或 support 指向）→ hard_fail + 推理星封顶 2⭐；
  否定（oppose 边）→ 计满分——「错误无惩罚、纠错有奖励」。

### 1.4 跨场景累积（09 号文档）

`ClueSystem.case_wall_state` 跨场景共享图谱（relations / graph_nodes / graph_derived_conclusions /
milestones_lit / verified / verdict 等）；`CaseReasoningRegistry.get_hypo_union_up_to(scene_id)`
聚合当前及之前场景的预设推断/结论并集；`WallBranchEvaluator._allowed_scenes(scene_id)`（:418）
取 scene1..N 前缀，保证场景 N 只评已解锁范围的链。

### 1.5 链清单（以代码为准，2026-11-19 实测）

`_legacy_branches()` 共 **16 条**：练习 2 条（CH01W/CH01M，practice:true）+ 正式 **14 条**。
core=true **10 条**（CH02/03/04/05/06/07/09A/09D/09E/09F），非 core 正式链 4 条（CH08/CH09A2/CH09B/CH09C）。

⚠️ **10 号文档表格与代码已漂移**：10 号写 CH09A「分支·否」，代码为 core:true；CH06（场景三 B 组专链）
与 CH09A2（凶手=北岸马车夫）是 10 号成文后补入的。Phase 1 搬运时以代码为准并回写 10 号文档。

## 2. 诊断：七个断点（墙为何推导不了「推理进程」）

### 断点 1（最根本）：判定与推进完全解耦

`detective_scene.gd:522-533` `_default_wall_verify()`：

```gdscript
_ui.show_notification("推理验证结果：" + entry[0])   # verdict 只换通知颜色
var advance := _in_reasoning_phase() or (_clues.size() >= hotspots().size())
if advance:
    _advance_now()                                    # 与 verdict 无关，恒推进
```

- scene2 覆写版（`scene2.gd:495-506`）只按四档换台词（`_show_scene2_verdict_dialogue`），播完仍按
  advance 无条件推进（:535 `_advance_now()`）。
- **scene3~scene8 完全没有消费 verdict 的代码**（grep 全项目验证）。
- 推进闸门本身设计合理（推理阶段或线索收满才推进，防「观察期开墙卡死」），问题不在推进，在于
  **verdict 没有任何下游**。

### 断点 2：里程碑一次性全亮，且与真相表零映射

`wall_verify.gd:267-270`：仅整体 VERIFIED 时 `for m in owner._milestones: m["lit"] = true` 全部点亮，
无中间态。milestone id（S2-1..S2-8 / S3-1..S3-7 / S4-1..S4-4 / S5-1..S5-4 / S6-1..S6-3 /
S7-1..S7-4 / S8-1..S8-4，共 34 条）在各场景 `reasoning_hypothesis()` 声明，与真相表节点**零映射**
（S2-1 等 id 在 case_branch_truth.gd / reasoning_chains.gd / case_reasoning_registry.gd 中 grep 零命中）
→ 无法表达「玩家推到了第几步」。

### 断点 3：图谱默认视图下，玩家看不到任何进度

`reasoning_wall.gd:348-350`：

```gdscript
_right_panel.visible = false
_center_panel.visible = false    # "当前判定"标签在这里
_bottom_bar.visible = false      # 里程碑栏 + 星栏在这里
```

图谱是默认主视图（`_on_open_graph_view()` :961），且无任何代码路径把三栏切回 visible
（全项目 grep `.visible = false` 之外无赋值点）。图谱顶栏
（`graph_view_controller._build_top_bar`）只有视图 tab/焦点/面包屑/撤销重做/提交验证/返回/帮助，
**无任何进度/命中率/里程碑显示** → 玩家在墙内唯一的实时反馈是结论节点颜色。

### 断点 4：图谱着色是另一套口径（双口径分裂）

`graph_view_data._compute_verdict()`（:157）是独立旧计数法：contradict/oppose 边>0 → 0；
support（关联线索+support 边）≥3 → 3；≥1 → 2；否则 1。它优先返回 `owner._verdict`，
但 `GraphViewController._verdict` 声明为 -1（:59）且全项目只在 :343 赋 -1，**从不更新**
→ 图谱结论着色恒走旧计数口径，与最终评分（WallBranchEvaluator 的 R 口径）分裂：
玩家看到「结论绿了」（乱连 3 条 support 也绿），提交后可能是「矛盾冲突」。
违反 10 号文档的核心原则「评分看整体对错，不看关系数量」与 11 号文档「单一事实源」约束。

### 断点 5：星级粒度 ≠ 真相链粒度

`StarRatingSystem.chains` 的 key 是场景级 chain_id（各场景 `reasoning_hypothesis().chain_id = scene_id()`，
共 7 个：scene2..scene8；场景一练习墙无 chain_id，`submit_chain` 守卫直接 return）。
`get_max_total_stars()` = `chains.size() × 9` → 实际满星 63⭐，而注释写「默认 14 链 => 126⭐」。
真相表 16 条链与星级 7 条链是两套粒度，推理星在场景 N 是「截至 N 的全链聚合 R」单值，
无法回答「第几条链推到几成」。

### 断点 6：跨场景链在早期场景被结构性扣分

CH03「来客特征（多场景综合）」标在 scene2 且 core:true，真相含 **17 项 T**（11 边 + 6 个 hypo/concl
节点），其中 3 条边的线索在场景二物理上不存在：

| 不可建边 | 线索归属场景 |
|---|---|
| c309 → H2-05 | scene3（血字字迹身高锚点） |
| c311 → H2-06 | scene3 |
| C_SOTCB_402 → H2-05 | scene4（醉汉身高 6 英尺交叉验证） |

→ 场景二 CH03 单链 R 上限 ≈ 14/17 ≈ **82.4%**，与 VERIFIED 阈值 80% 踩线：叠加 CH02 的任何一处
瑕疵（一分母项 +1 → 28/35=80.0% 恰好过，再错一项 → 77.8% 掉 SUPPORTED），场景二「正确🌟」
实际上要求近乎完美解。场景三/四后 R 可继续升高（case_wall_state 跨场景累积），
但 `case_branch_log["scene2"]` 永远记录的是提交当刻的低值快照。

### 断点 7：进程素材已生产，但只用于结算

`StarRatingSystem.record_branch_progress()`（:95）每次提交都把
`{ratio, stars, summary, hard_fail, per_branch}` 写进 `case_branch_log[scene_id]`，
per_branch 每链含 `ratio/hit/built/truth/missing_nodes/missing_edges/reversed_edges/extra_edges/matched_edges`
——这就是现成的「推理进程账本」（且经 `save_manager.gd:220-221` 持久化、沙箱回收后云端可恢复）。
但它的唯一消费者是场景八结局面板（`detective_scene.gd:1131` 一带 `_show_scene_rating`）。
**生产了 8 个场景的过程数据，只放了 1 次终局放映。**

### 附：剧情侧现有分支机制与墙无关

scene4 六方向追问 `_asked_directions`（time/look/cloth/carriage/scene/other，:41）、
scene5 跟踪决策 `_route`/`_tracked`、scene6 消费 `scene4_route == "C"` ——全部由玩家点选驱动，
与推理墙数据零耦合。「案件进度轴」在代码中无任何实现（grep 仅命中文档）。

## 3. 设计方案（按用户三条裁定）

### 3.1 设计总纲（2026-11-19 用户裁定，永久有效）

1. **文档纪律**：非必要文档不主动创建。
2. **14 条正式链修正顺序——先修后搬**：问题在 legacy 表（当前运行权威）修完、经现有探针回归后，
   再机械搬入链库（`validate_all()` 收口）；搬运与修数据不混同一批提交。
3. **剧情与推理墙松耦合（设计总纲）**：正确推理引导主线剧情，不正确推理引导**旁支剧情**
   （不是惩罚，是另一条内容路径）——现实侦破就是在试错中分辨哪条推理正确，都选对只有福尔摩斯
   做得到，不是普通玩家。玩家沿迷惑分支行不通时能「**返回**」正确（或玩家认为正确）的分支继续剧情，
   **错误永不卡死游戏**。墙的 verdict/命中率只作为剧情分支的输入信号之一，不做硬闸门
   （防重蹈场景二卡死覆辙）。

### 3.2 架构：墙只写账本，剧情只读账本

```
推理墙（wall_state/wall_verify）                    剧情层（scene2~8）
      │ 提交验证                                            │
      ▼                                                     │
WallBranchEvaluator.evaluate() ──► _last_branch ──► record_branch_progress()
      │                                                    │
      ▼                                                    ▼
StarRatingSystem（单例+持久化）  ◄── 只读接口 ──  场景脚本分支决策
  · case_branch_log[scene_id].per_branch           · get_case_branch_log()
  · chains[chain_id] 三维星                        · get_chain_stars(chain_id)
  · get_total_stars()/get_max_total_stars()        · _advance_now()（保持不动）
```

- **解耦层就是已有的 `StarRatingSystem` 单例**：墙负责写入，场景只读，方向单一。
- **推进逻辑保持现状**（`advance := _in_reasoning_phase() or 线索收满 → _advance_now()`），
  保证任何判定下剧情都能继续——这是「错误不卡死」的结构保证。
- **verdict 的消费从「是否推进」挪到「推进后走哪条内容路径」**。

### 3.3 verdict → 内容路径映射

| 提交结果 | 内容路径 | 实现 |
|---|---|---|
| VERIFIED(3) | 主线确认台词（现状 scene2 四档已有） | 保留 |
| SUPPORTED(2) / INSUFFICIENT(1) | 主线继续 + 华生标注存疑 + **旁支钩子开放** | 新增 |
| CONTRADICTORY(0)（采纳误导） | **进旁支剧情**：追查错误方向 → 旁支以「此路不通」的证据收束（原著同款桥段）→ 回主线 | 新增 |
| （旁支内 negate 误导项） | 回墙后纠错 → 洞察加成（机制已有，缺内容引导） | 串接 |

关键：**所有分支最终汇入 `_advance_now()`**——旁支是绕路，不是死路。误导项素材现成且原著背书：
H3-C10「与 RACHEL 的女人有关」（雷斯垂德观点，原著《血字的研究》经典错误方向）、
H2-M2「徒步踏泥报童」、H4-M1「有个女的」（困难模式概率误导）——每条误导项天然就是一条旁支任务的钩子。

### 3.4 剧情挂载点（全部现成，不造新机制）

| 挂载点 | 现状 | 挂载后 |
|---|---|---|
| scene4 六方向追问 `_asked_directions` | 六方向无条件可问 | CH07 相关推断未建立 → 兰斯只答表面方向；答对才给关键证词（问询深度由推理质量决定） |
| scene5 跟踪决策 `_route`/`_tracked` | 玩家点选 | CH09A/CH09A2 命中率决定华生的**默认建议**（最终仍由玩家定） |
| scene6 消费 `scene4_route=="C"` | 消费场景四选择值 | 保持；scene4 的 route 值改由「推理结果 + 玩家选择」共同派生 |
| 场景过渡对话 | 固定台词 | 按 verdict 分档（scene2 已有四档模板，可平移到 3~8） |

### 3.5 进程可视化（墙内）

- 图谱顶栏加「推理进程条」：全案 ΣR + core 链逐链 ratio 色块 + 洞察合成层完成度。
  数据源：`_last_branch.per_branch`（cb 已透传到墙，`wall_verify` 已用它渲染明细）。
- 「当前判定」标签与里程碑栏在图谱模式可见（迁顶栏或悬浮 chip），消灭断点 3。
- 图谱写色切同一评分源，消灭断点 4（见 Phase 0）。

### 3.6 里程碑 gate 化（从「一次性全亮」到「过程刻度」）

- 每条 milestone 增加 `gate` 字段：指向真相节点/边 id 数组（链库化后与真相表同一 id 空间）。
- 点亮条件：gate 引用的节点在玩家产物中（产出推断/落盘结论/命中边）即逐条点亮，
  替代「仅 VERIFIED 全亮」（可保留 VERIFIED 时剩余全亮作兜底）。
- `milestones_lit` 已有持久化键（`wall_state._persist_state` :100），但当前语义是
  「当前墙覆盖写」——跨场景累计需改 **merge 语义**（见 Phase 3）。
- 案件进度轴（06 文档 §3.3 M2+）：跨场景汇总 milestones_lit + case_branch_log，
  在卷宗/墙外入口展示全案推理进程（哪条链几成、哪个里程碑已立、哪些误导已排除）。

## 4. 实施路线（五个 Phase）

> 原则：口径层与数据层先行（不碰剧情结构），UI 与剧情挂载在后；
> 每个 Phase 独立提交、独立回归；涉及真相表数值口径变化的基线更新必须显式记录。

### Phase 0 · 口径统一（evaluator 层，不碰剧情，风险最低）

**目标**：消灭断点 4（双口径）与断点 6（跨场景链早期进分母）。

| 步骤 | 内容 | 改动点 | 验证 |
|---|---|---|---|
| 0.1 | **T 按已收集线索裁剪**：真相边 from 为 clue 且该线索尚未收集 → 记入 `unavailable_edges`，从 T 与 missing_edges 剔除（节点部分不受影响，hypo/concl 仍可产出）。`evaluate()` 增加参数 `collected_ids: Array`，`wall_state` 调用点传 `ClueSystem.get_collected()` 的 id 集 | `wall_branch_evaluator.gd`（evaluate :68 / _score_branch :308）、`wall_state.gd` 调用点 | 新增基线探针：修改前后 16 链 ratio 逐链 dump 对比；**预期场景二 CH03 上限回到 100%**；全链其他 ratio 不应有意外变化 |
| 0.2 | **图谱着色切同一评分源**：GraphViewController 在关系变更回调/`_persist_view` 时调用墙的 `get_verdict()`（`reasoning_wall.gd:271` 已有，委托 `_branch_verdict()`→WallBranchEvaluator）写 `self._verdict` → `graph_view_data._compute_verdict()` 已支持 `owner._verdict >= 0` 优先，无需改着色函数 | `graph_view_controller.gd`（:59 声明处 + 关系回调） | 场景二实测：乱连 3 条 support 不再变绿；与提交判定一致。性能：evaluator 为纯数据比对（16 链规模），毫秒级，拖边实时计算无碍 |
| 0.3 | 星级粒度注释修正（`get_max_total_stars` 实际 63 非 126）；真正的按链提交三星放到 Phase 1 链库化之后评估 | `star_rating_system.gd` 注释 | — |

## 5. 风险与红线

| 风险 | 等级 | 对策 |
|---|---|---|
| verdict 消费做成推进硬闸门 → 重蹈场景二卡死覆辙 | **禁令** | 推进逻辑一行不改（断点 1 的 advance 判定保留）；verdict 只分流内容 |

| 图谱反馈「变严格」（乱连不再变绿）被玩家感知为退化 | 低 | 实为纠正误导性反馈；提交判定文案已区分四档，配合进程条解释 |
| 里程碑 gate 标注工作量（34 条） | 中 | 场景二试点跑通模式后铺开；链库化后 gate 与真相节点同 id 空间，标注可对照 `reasoning_chains_all_scenes.md` |

| 存档兼容（milestones_lit merge、基线变化） | 低 | merge 语义对旧档 id 数组天然兼容；ratio 变化只影响展示与结局档位，不影响存档结构 |

## 6. 验收标准

1. **口径**：场景二完美解可达 VERIFIED 且非踩线（CH03 上限回 100%）；图谱着色与提交判定同源（同一 verdict）。
2. **可见性**：图谱模式可见 ΣR 进程、逐链 ratio、当前判定、里程碑进度；误导项被采纳有即时视觉反馈。
3. **里程碑**：gate 命中即逐条点亮，与真相节点一一对应；跨场景累计不丢（merge 语义）。
4. **剧情**：采纳误导 → 进旁支 → 「此路不通」收束 → 回主线全流程可通，全程无卡死；旁支出口全部汇入 `_advance_now()`。
5. **回归**：`validate_all()` 零闭合错误；16 链 ratio 基线全表记录（Phase 0 为有意更新）；现有探针
   （t_flow_diff / t_validate_m / t_drag_seq_repro / test_case_branch_log_persist）零回归。
6. **存档**：旧档读入不崩、不丢里程碑/账本数据；沙箱回收后云端恢复路径不受影响。
