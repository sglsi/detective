| 来源 | 要求 |

## 二、开发设计现状（运行时机制核对）

**实际架构（已落地、内部自洽）：**
- `star_rating_system.gd`：**9 星简化模型**（`observation_score` 上限 115 加权 / `reasoning_score` 上限 14 / `insight_score` 上限 7），`get_stars(dim)` 按占比 0.3/0.6/0.9 给 0-3 星；`get_total_stars()` 满分 9；`evaluate_badges()` 写 `badges` 数组 + `competitive_score`；`get_adjusted_total_stars()` = round(总分 × 难度倍率)。
- `badge_system.gd`：独立 autoload，监听 `SystemEventBus.case_completed` → 调 `evaluate_badges()` → 累积已解锁徽章集合 + 持久化 + 广播。运行时徽章采用 `StarRatingSystem.Badge` 枚举（锐眼/推理大师/深掘者/完美通关/速通者/无提示大师/首案告破），与 08 §3.10 另列的 7 枚命名不重合（统一属后续事项，见 §五）。
- `ending_system.gd`：独立 autoload，监听 `case_completed` → 按 `get_total_stars()/9` 占比判四档结局（与难度无关，符合设计）。
- 触发链：`GameManager.end_case()` → `case_completed` → `BadgeSystem` + `EndingSystem` 同时消费，**`evaluate_badges()` 确实在案件结束时被调用**。

**与设计偏差（本次要解决的）：**
1. **P3.1 回归（测试已坏）**：`test_ending_system.gd` 写死 `observation_score = 45` 期望 3 星，但 P3.1 把 `max_observation` 改为 115 → 45/115≈0.39 → 仅 1 星；且其「杰出(7星)」用例写 `insight_score = 3`（3/7=0.43→2 星），总分 8 → 传奇，与期望「杰出」矛盾。**该测试在 P3.1 后必然失败 2/4 断言，此前因沙箱无法跑测试未被发现。**
2. **缺失 GDD §2.6.5 综合等级**：`名侦探/合格侦探/继续推理` 三个综合等级在代码层面**无任何实现**——只有 `EndingSystem` 的四档结局（按占比）。两者是设计上并列的两套评价出口（综合等级看总星数、结局看占比），不可互相替代。
3. **缺失 GDD §2.6.2 简单模式观察门槛**：观察之星 3 星门槛恒为 0.9，未对 EASY 降到 0.8。

**设计内部张力（已记录，非本次新引）：**
- GDD §2.6.2 要求「简单模式降观察 3 星门槛」；但三难度哲学又说「难度不影响数据层，只影响系统替玩家做了多少事」。本改动严格按 GDD §2.6.2 字面实现（仅降观察满星门槛），竞技维度仍由 `get_adjusted_total_stars`（倍率）独立承担，二者不冲突。

## 三、改动设计（diff 级）

### 3.1 `autoload/star_rating_system.gd`
**a) `get_stars()` — 观察之星 EASY 降门槛（GDD §2.6.2）**
```gdscript
func get_stars(dimension: RatingDimension) -> int:
	var ratio: float
	var top_threshold: float = 0.9   # 3星门槛
	match dimension:
		RatingDimension.OBSERVATION:
			ratio = float(observation_score) / float(max_observation)
			if DifficultyManager != null \
			   and DifficultyManager.current_difficulty == DifficultyManager.Difficulty.EASY:
				top_threshold = 0.8
		RatingDimension.REASONING:
			ratio = float(reasoning_score) / float(max_reasoning)
		RatingDimension.INSIGHT:
			ratio = float(insight_score) / float(max_insight)
	if ratio >= top_threshold: return 3
	elif ratio >= 0.6: return 2
	elif ratio >= 0.3: return 1
	return 0
```
> 仅观察维在 EASY 下 3 星门槛 0.9→0.8；推理/洞察不变。对满星（ratio=1.0）与零分（ratio≈0）用例无影响，既有测试安全。

**b) 新增 `get_evaluation_grade()`（GDD §2.6.5）**
```gdscript
func get_evaluation_grade() -> Dictionary:
	var total := get_total_stars()
	var three_star_dims := 0
	for dim in [RatingDimension.OBSERVATION, RatingDimension.REASONING, RatingDimension.INSIGHT]:
		if get_stars(dim) == 3:
			three_star_dims += 1
	if total >= 7 and three_star_dims >= 2:
		return {"grade": "master_detective", "name": "名侦探",
		        "description": "贝克街名侦探称号，解锁《四签名》预告 + 开发者评论。", "can_replay": true}
	if total >= 4:
		return {"grade": "qualified_detective", "name": "合格侦探",
		        "description": "福尔摩斯认可，案件正常结案。", "can_replay": true}
	return {"grade": "keep_investigating", "name": "继续推理",
	        "description": "推理仍有疏漏，可回溯重新推理，不强制结束。", "can_replay": true}
```
> 纯新增，不改动既有行为；与难度无关（用原始总星数），与 `EndingSystem`（按占比）并存互补。

## 五、残留事项（不在本次范围，已记录）

1. **徽章命名统一**：运行时 `StarRatingSystem.Badge`（锐眼/推理大师…）与 08 §3.10 的 `BadgeID`（初出茅庐/神枪手/博闻强识…）是两套不重合的 7 枚定义。统一属「后续事项」（badge_system.gd 注释已标注）。本次未动，避免违反「单一机制」与引入回归。
2. **`SPEED_RUNNER` 徽章死定义**：枚举存在但 `evaluate_badges()` 从不授予（缺计时基础设施）。需先有通关计时器才能落地。
3. **`08 §3.6` 的「每条推理链 126 星」模型**：设计描述 per-chain 模型，但运行时代之以 9 星案件级模型（已在 P3.1 加权化）。这是架构级简化，非本次补齐范围；若需 per-chain 明细需重做推理墙→星级喂数链路。
4. **结局占比与综合等级并存**：当前 `EndingSystem`（占比）与新增 `get_evaluation_grade()`（总星数）是两个设计出口，UI 层需分别展示或择一为主；未做 UI 接线（scene8 结算页待接入）。
5. **scene1-3 不计观察分**（P3.1 已记）：`score_awarded` 信号未接线，观察分仅 scene4-8 计入，`max_observation=115` 据此设定。
