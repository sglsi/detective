# 第一部分 测试方案

## 1.1 修订动因

v1.0 是一份"功能清单"，不是可执行的测试方案。三轮实测暴露了三类系统性问题：

| 问题类型 | 实例 | 后果 |
|---|---|---|
| 判据不可判定 | L03「间距默认 15px」、L10「缩放比合适」 | 测试写完也无法给出 PASS/FAIL |
| 预期与实现相反 | R10 target 边参与布局、L2-03「EASY 显示分偏高」 | 照文档写测试必然误报 |
| 覆盖表失真 | L03 标"已覆盖"，实测零覆盖；D/E/L/P 覆盖率整体低估 | 缺口被掩盖，重复投入已覆盖项 |

因此 v2.0 的首要目标不是增加用例数量，而是让**每条用例都能落到一种确定的验证方式和一个确定的判定式**。

## 1.2 四层测试模型

| 层级 | 驱动方式 | 能验证什么 | 不能验证什么 | 典型用例 |
|---|---|---|---|---|
| **U** 算法单元 | `SceneTree` 脚本直接 preload 目标脚本，构造字典入参，调纯函数 | 布局算法、评分公式、判定映射、数据结构 | 视图尺寸、字体换行、渲染、交互 | D/E/H/L03/L2 |
| **I** 集成 | `SceneTree` + `await process_frame` + `add_child(gv)` 建真实 Control 树 | 布局→去重叠→钳制整条流水线、视图尺寸参与的高度模型 | 真实鼠标事件、跨场景流程 | L01/L02/L04~L08 |
| **E** 端到端 | 场景脚本 + `Input.parse_input_event` 投递真实事件 | 拖拽建边、关墙重开、跨场景推进 | 视觉观感、帧率 | R/P/V/L1/L3 |
| **M** 人工 | 浏览器实机操作 | 动画、配色、观感、帧率、触屏手感 | 精确坐标 | U/V/L10/L11 |

**分配原则**：能用 U 就不用 I，能用 I 就不用 M。只有"必须由人眼判断"的项才归 M，且必须在用例里写清人工判读的具体观察点，禁止"看起来正常"这类表述。

## 1.3 测试环境

```bash
# 单元/集成（无渲染，最快，CI 可用）
godot --headless --path godot_project -s tools/<suite>.gd

# 需要真实 Control 树的集成（走 .tscn 场景）
godot --headless --path godot_project res://scenes/<name>.tscn

# 需要真实鼠标事件
godot --headless --script res://tools/test_wall_drag.gd
```

探针脚本骨架（`SceneTree` 型）：

```gdscript
extends SceneTree
func _initialize() -> void:
    await process_frame          # 必须：等引擎就绪，否则 viewport/字体尺寸为 0
    # ... 构造与断言
    quit(0 if _fail == 0 else 1)
```

**退出码约定**：`0` 全通过，非 `0` 存在 FAIL。套件末尾必须打印一行机器可读汇总，例如 `L03_RESULT PASS (9/0)`，供批跑脚本 grep。

## 1.4 判定口径铁律（六条）

这六条来自实测踩坑，违反任意一条都会产出无效结论。

### 铁律 1：坐标断言必须带容差

浮点布局不存在精确相等。统一容差：

| 断言类型 | 容差 |
|---|---|
| 同列判定（中心 x 相等） | ≤ 1.0 px |
| 位置保持（折叠/展开/重排后不变） | ≤ 0.5 px |
| 间距下限 | 不设上容差，只判 `实际 ≥ 阈值` |
| 重叠判定 | 严格 `> 0` 才算重叠（边贴边不算） |

### 铁律 2：节点高度必须取真实高度，禁止用固定值

布局的真实高度来源是 `graph_view_layout.gd::_real_node_height(id)`，取值顺序：

1. 视图已就绪 → `owner._node_views[id].size.y`
2. 视图未就绪 → `_meas_lab` 字体度量（`+14.0` 行距）
3. 字体不可用 → 兜底 `412.0`

**任何涉及高度的断言，必须调用 `_real_node_height` 取实测值后代入判定式，不得写死 412 / 400 / 260。** 写死高度会让用例在真实渲染下静默失效。

### 铁律 3：headless 下禁止通过注入视图尺寸来伪造高度差异

`_node_views[id].size.y = 840` 会被 Control 的 `minimum_size` 约束 clamp 回去，**赋值成功但布局读到的仍是原值**，表现为"改了没用"。这类"伪 FAIL"曾导致 L03 被误判为"headless 测不了高度差异"。

**正解**：绕开视图层，直接对算法函数传自定义高度字典。

```gdscript
# 布局内部签名
_pack_contour(root_id, child_map, depth_of, est_h: Dictionary, node_by_id)
# est_h = {"A": 120.0, "B": 840.0} 即可测混合高度
```

**结论**：凡"只有真实渲染才能构造的输入"，一律下沉到 U 层用函数入参构造，不上溯到视图注入。

### 铁律 4：禁止放宽阈值凑通过

当实测值与预期不符，只有两种合法结论：

- **实现有缺陷** → 记缺陷、修实现、用例不动。
- **用例预期写错** → 改用例，并在修订记录里写明"原预期错在哪、依据是什么"。

**禁止**把 `≥ 80` 改成 `≥ 15`、把 `≤ 1px` 改成 `≤ 5px` 来让套件变绿。这类修改会永久掩盖回归。

### 铁律 5：优先真实场景数据，禁止用最小人造图冒充

人造 3 节点图无法暴露真实退化。实测教训：L02 若只用"单链 4 节点"，永远发现不了"两条线索支撑同一推断被串成单链"——该缺陷只在 `scene2` 的 `H2-01`（`gate_clue_ids=["c201","c202"]`）这类真实数据上出现。

**规则**：每个布局用例必须至少有一个用例实例使用 `scene2~scene8` 的真实墙数据（`ReasoningChains.build_wall_dict`），人造图只作为边界补充。

### 铁律 6：FAIL 必须打印实测值

断言辅助函数统一形态：

```gdscript
func _chk(cond: bool, name: String, actual: Variant, expect: String) -> void:
    if cond: _ok += 1
    else:
        _fail += 1
        print("FAIL | %s | 实际=%s | 预期=%s" % [name, str(actual), expect])
```

只打印"FAIL"不打印实际值的套件，视为不可交付。

# 第四部分 用例编写规范（新增）

供后续新增用例时遵循。

1. **一个用例 = 一个断言簇**，失败时能唯一定位。禁止"顺带检查"。
2. **预期必须含具体数值或结构条件**。出现"合适""正常""合理""大致"的用例一律视为未完成，需重写。
3. **前置条件必须是可构造的状态描述**，不写"多节点""某链"这类模糊说法，要写"`scene2` 的 `H2-01`（`gate_clue_ids=["c201","c202"]`）"。
4. **真实数据优先**（铁律 5）。每个布局用例至少一个真实墙实例。
5. **同一断言不得在两个套件里用不同口径**（如 L03 的 15px vs 80px）。口径只在本文档定义，套件引用。
6. **已知限制必须显式标注** `KNOWN_LIMITATION`，并写明"目标预期"与"现状预期"，不得直接删用例。
7. **功能缺口必须先标注"待实现"**，再给"现状预期（不崩溃）"作为兜底回归，禁止把未实现写成已通过。
